# AI 自然语言填表 · 方案

> 目标：用户用一句中文口语，把表单自动填好。
> 例如输入「我下周三到周五请病假，感冒发烧」，请假表单的四个字段自动填上。

---

## 一、为什么这么设计

### 1. 不让 AI 直接操作界面，只让它输出 JSON

**如果让 AI 去"点"页面**：它可能填错框、可能把「病假」填进日期里、可能清掉用户刚打的内容。
**输出 JSON 就不一样**：字段名是写死的，多一个少一个、类型不对，代码一眼就能发现。

```
用户说一句话
     ↓
   AI 只干一件事：把这句话变成一段 JSON
     ↓
{ "type": "病假", "startTime": "2026-10-14", ... }
     ↓
   代码把这段 JSON 塞进表单
     ↓
  用户看一眼，自己点提交
```

### 2. AI 填的数据必须走原有校验

请假表单本来就有 `rules` 和 `disabledEndDate`。
**AI 就算返回「结束时间早于开始时间」，也会被表单当场标红拦住。**

这就是"AI 只当代笔、不当代签"。

### 3. Key 永远不下发到浏览器

前端代码是打包后发给浏览器的，**写在里面的 key 等于公开**。
所以中间必须有一个代理：

```
浏览器  →  代理服务（key 存在这里的环境变量）  →  DeepSeek
```

代理先用本地 Python 小服务开发，跑通后贴到阿里云。

---

## 二、JSON 契约（前后端的约定）

前端和后端只认这一段格式，**换模型、换语言都不用改前端**。

### 请求

```
POST /api/ai/fill
Content-Type: application/json

{
  "target": "leave",                        // leave | todo
  "text": "我下周三到周五请病假，感冒发烧",
  "history": [                              // 可选，多轮对话用
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." }
  ]
}
```

### 响应

```json
{
  "ok": true,
  "source": "ai",                           // ai | local（本地规则兜底时是 local）
  "reply": "已经帮你填好了，确认一下再提交。",
  "fields": {
    "type": "病假",
    "startTime": "2026-10-14",
    "endTime": "2026-10-16",
    "reason": "感冒发烧"
  },
  "missing": []                             // 没解析出来的字段名
}
```

失败时：

```json
{ "ok": false, "reply": "AI 服务暂时用不了，已切换本地解析", "fields": {}, "missing": [] }
```

### 字段定义

**target = `leave`（请假）**

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `type` | string | `事假` \| `病假` \| `年假` |
| `startTime` | string | `YYYY-MM-DD` |
| `endTime` | string | `YYYY-MM-DD`，不得早于 startTime |
| `reason` | string | 5 - 200 字 |

**target = `todo`（待办）**

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `title` | string | 2 - 40 字 |
| `description` | string | 0 - 200 字（可空） |
| `category` | string | `工作` \| `活动` \| `学习` \| `文档` \| `其他` |
| `priority` | string | `高` \| `中` \| `低` |
| `assignee` | string | 组员姓名 |
| `dueDate` | string | `YYYY-MM-DD` |
| `status` | string | `待办` \| `进行中` \| `已完成` |

> **没解析出来的字段填 `null`**，并在 `missing` 里列出字段名。
> 前端只覆盖有值的字段，**不会清掉用户已经填好的内容**。

## 三、Prompt 设计要点

1. **必须告诉它今天几号。**
   「下周三」这种相对日期，模型自己猜很容易偏一周。
   system 里写死：`今天是 2026-10-08 星期四。`
2. **要求纯 JSON，不要 markdown 代码块。**
   否则返回里会带 ``` 包裹，前端还得剥一层。
3. **给出闭集选项**（如 `事假|病假|年假`），不要让它自由发挥。
4. **明确"没说就填 null"，禁止编造。**
   模型很爱自己补一个理由，这会污染数据。

## 四、降级策略（重要）

**AI 挂掉时页面必须还能用**，否则答辩现场断网就翻车。

```
调 /api/ai/fill
   ├─ 成功  → 用返回的 fields，界面标记「AI」
   └─ 失败  → 走本地规则解析，界面标记「本地」
              （超时、500、没配 key、断网，都走这条路）
```

本地规则解析器覆盖：

- **类型**：关键词匹配（生病/发烧/不舒服 → 病假，回家/办事 → 事假）
- **日期**：绝对日期、今天/明天/后天、下周三、区间（X到Y）、时长（三天）
- **原因**：剩下的文本

它解析不了的，就交给用户自己填。

## 五、安全清单

- [x] Key 只存在代理服务的环境变量里（`DEEPSEEK_API_KEY`）
- [x] 前端代码里**没有任何 key**
- [ ] `.env` 必须写进 `.gitignore`，**永远不提交**
- [x] AI 返回的数据经过白名单过滤（只取契约里定义的字段）
- [x] 日期做格式校验，非法值直接丢弃
- [x] **不自动提交**，必须用户手动点

## 七、答辩时可以讲的三个点

1. **为什么不让 AI 直接操作界面** —— 不可控、不可校验
2. **为什么让它输出 JSON** —— 结构固定，能直接复用已有的表单校验
3. **为什么必须有降级和人工确认** —— AI 只代笔，不代签
